## 二、架构设计

### 2.1 整体链路

```
前端 ChatWidget
   │  POST /api/chat/ask {question, history[]}
   ▼
ChatServiceImpl.ask()
   ├─ tryAgent()  ──成功──▶ ChatAnswerVO（智能体回答 + 卡片）
   │     │
   │     ▼
   │  AgentOrchestrator.chat()
   │     ├─ 组装 system prompt + 多轮历史 + 用户问题
   │     ├─ 带 7 个工具定义调用 LLM
   │     ├─ 模型返回 tool_calls → 执行 → 回填结果 → 再调 LLM
   │     └─ 最多 3 轮，收敛后返回文本 + 工具原始结果
   │
   └─ 失败/未启用 ──降级──▶ route()（原有规则引擎，断网可用）
```

### 2.2 工具清单（全部实时查库）

| 工具 | 作用 | 数据来源 |
| --- | --- | --- |
| `search_dishes` | 按菜名/分类/简介搜菜 | `dish` + `dish_review` 实时统计 |
| `list_stalls` | 档口列表（含窗口号归一化） | `canteen_stall` + 评价统计 |
| `list_stall_dishes` | 某档口全部在售菜 | `dish` 按 `stall_id` |
| `get_rankings` | hot / avoid / new / stall_top | `StatsServiceImpl` 红黑榜逻辑 |
| `search_faq` | 制度知识库检索 | `sys_faq` |
| `list_notices` | 最新公告 | `sys_notice` |
| `get_overview` | 食堂整体统计 | `StatsMapper.selectOverview` |

**关键设计**：卡片（`ChatItemVO`）的数据取自工具原始返回结果，**不取自模型输出**。
即使模型说错数字，卡片上的价格/评分仍是数据库真值。

## 五、踩坑与解决方案（重要，供答辩讲解）

### 坑 1：结构化提示词会让 7B 模型「只说话不调工具」

**现象**：用「【最高原则】/【工具使用】/【回答风格】」分节 + 大量"严禁/必须"的提示词，
问「宫保鸡丁多少钱」，模型返回 `finish=stop, toolCalls=0`，直接编造"10元"（实际 12 元）。

**定位过程**：二分法逐段测试提示词，发现 S1~S5 分段单独用都正常，**完整拼接就失效**。

**解决**：改成紧凑自然语言陈述句，不用 Markdown 分节。

### 坑 2：带多轮历史时，模型 30%~50% 概率「忘记调工具」

**现象**：同一个问题，无历史时答对（22元），带历史时编造（18元）。
日志显示 `finish=stop toolCalls=0 contentLen=14`。

**根因**：7B 模型会模仿历史中 assistant「直接说话」的模式，跳过工具调用。

**解决**：协议层强制兜底——首轮未调工具且问题需要数据时，
用 `tool_choice=required` 强制重试一次，然后**直接进入 summarize 阶段**
（不传 tools，只让它总结工具结果）。

> 注意：`tool_choice=required` 单独用不够，第一次实现时 `continue` 回到主循环，
> 第二轮仍是 `auto`，模型又不调工具，问题依旧。必须走独立的收敛路径。

### 坑 3：模型会推测工具没返回的属性

**现象**：问「干煸豆角辣不辣」，描述里只写"四季豆干煸，配肉末"，
模型答"比较辣"——这是推测。

**解决**：提示词明确"工具里没写的属性不要猜，说「描述里没写，建议问档口」"。
修复后回答："描述里没写辣不辣，建议问问档口。"

### 坑 4：模型输出 Markdown 符号

**现象**：避雷榜输出 `**缤纷时蔬沙拉**`，前端按纯文本渲染，星号会露出来。

**解决**：提示词 + 代码层 `sanitize()` 双重保险，正则剥离 `**`、`#`、`` ` ``、列表符。

### 坑 5：「13号窗口」查不到

**现象**：SQL 里 `window_no LIKE '%13号窗口%'` 匹配不到 `window_no='13'`。

**解决**：工具层增加窗口号归一化（`extractWindowNo` + `stripLeadingZeros`）。

### 坑 6：知识库检索「先到先得」导致答非所问

**现象**：问「评价可以修改吗」，`search_faq` 按关键词「评价」命中了 id=1「怎么给菜品打分评价」，
模型据此回答「不可以直接修改」，与知识库原文（"可以随时重新提交来修改"）**完全相反**。

**根因**：原实现遍历到 5 条就 break，没有按相关度排序。

**解决**：改为打分排序——问句整体相似度 ×10、问句包含关键词 +6、关键词表命中 +4、
动作词（修改/删除/取消/几点）同时出现 +3，取 Top3。

### 坑 7：知识库无匹配时不应「随便给几条」

**现象**：问「藜麦牛油果碗多少钱」（不存在的菜），`search_faq` 兜底返回了
「菜品价格在哪里看」，模型把它当答案念出来。

**解决**：无匹配时返回空 + `hint` 提示模型如实说没找到，不再退化为「随便给几条」。

### 坑 8：模型把菜名截短 / 误判成榜单意图

**现象**：库里新增一道菜叫「验证用新菜」，问「验证用新菜多少钱」，
模型却调用 `get_rankings({"type":"new"})`，回答成"新菜宫保鸡丁 12 元"——
菜名里的「新菜」二字让模型误判成"查新菜榜单"。

换个问法，模型又会把关键词截短成「新菜」，`LIKE '%新菜%'` 命中一堆无关的菜。

**定位过程**：
1. 先用 SQL 确认数据在库、`status=1`、`deleted=0`，API 也能搜到 → 排除数据问题
2. 打开 DEBUG 日志打印工具名+参数，发现调用的是 `get_rankings` 而不是 `search_dishes`
3. 直连 API 复现，确认模型传的 `keyword` 是 `"新菜"`（丢了「验证用」前缀）

**解决**：双保险
1. `AgentTools.searchByRawQuestion(rawQuestion)` —— 用**用户原始提问**在全部菜名里做包含匹配，
   菜名越长优先级越高（避免「新菜」这种短名抢先命中）
2. 在工具执行处，只要原始提问能精确命中某个菜名，就**覆盖**模型选错的工具结果，
   并把卡片数据也换成精确结果

这样即使模型选错工具或截短关键词，最终答案和卡片仍然正确。

**验证**：修复后「验证用新菜多少钱」正确返回 23.50 元；
「有什么新菜」「今天有什么推荐」「哪些菜要避雷」等列表类问题不受影响（无回归）。

## 七、已知限制与建议

### 7.1 当前限制

| 限制 | 影响 | 建议 |
| --- | --- | --- |
| 7B 模型能力有限 | 复杂多跳推理（如"比宫保鸡丁便宜且评分更高的菜"）易出错 | 演示时避免此类问题，或升级到 14B/32B |
| 无流式输出 | 最长等待 6 秒，前端只能显示 typing | 可选：改 SSE 逐字输出（模型已支持，见预实验） |
| 无对话持久化 | 刷新页面历史丢失 | 课堂演示够用；需要可存 Redis |
| 工具结果硬截断 6000 字符 | 极端情况下数据被截 | 当前库规模（52 菜）远未触及 |
| 单机内存限流 | 重启后计数清零 | 演示够用 |

### 7.2 演示建议

1. **重点展示「新数据识别」**：现场往数据库插一道菜，立刻问智能体，效果最震撼
2. **展示降级**：把 `canteen.agent.enabled` 改成 `false` 重启，证明断网可用
3. **避免的提问**：涉及多条件组合筛选、需要跨表复杂计算的问题
4. **可讲的坑**：坑 1 和坑 2 是很好的技术深度体现，说明做过真实调优而非调包
