# 答辩专项：大模型智能客服（会问什么 / 怎么答）

> 版本：小组集中开发版（`canteen-feedback-system`）
> 模型：智谱 `glm-5.3-flash`（OpenAI 兼容协议，原 `Qwen/Qwen2.5-7B-Instruct` 硅基流动）
> 一句话定位：**不是把数据塞给大模型让它背，而是让模型调工具实时查库，答案和卡片都来自数据库。**

---

## 〇、先用 30 秒讲清整体架构（开场必讲）

```
学生提问
  ↓ POST /api/chat/ask/stream（SSE 流式）
ChatServiceImpl.askStream
  ↓ 先试 Agent
AgentOrchestrator.chatStream
  ↓ 循环最多 3 轮
LlmClient（OpenAI 兼容 /chat/completions）→ glm-5.3-flash
  ↓ 模型返回 tool_calls
AgentTools 执行 7 个查库工具（实时 SQL）
  ↓ 工具结果回填给模型
模型生成自然语言 → 前端逐字显示
  ↓ 任何一步失败
自动降级到本地规则引擎（关键词 + 二元组匹配）
```

三个关键词记住：**工具调用（不编数据）、流式输出（不干等）、自动降级（不会挂）**。

## 一、接入类（必问）

**Q1：大模型是怎么接进来的？用了哪家？**
- 智谱开放平台 `https://open.bigmodel.cn/api/paas/v4`，模型 `glm-5.3-flash`；切换前用的是硅基流动的 `Qwen/Qwen2.5-7B-Instruct`。
- 走的是 **OpenAI 兼容协议**（`/chat/completions`），所以换厂商只改配置不改代码（`docs/模型切换测试报告-GLM5.3Flash.md` 有实测记录）。
- 后端自己用 JDK HttpClient 发请求（`agent/LlmClient.java`），**没有引入任何厂商 SDK**，避免依赖绑死。

**Q2：接入改了哪些文件？**
| 文件 | 作用 |
|---|---|
| `application.yml` | `canteen.agent.*` 配置：开关、base-url、api-key、model、超时、轮数、温度 |
| `agent/LlmClient.java` | HTTP 调用 + SSE 流解析 + 异常封装（`LlmException`） |
| `agent/LlmProtocol.java` | 请求/响应 DTO（messages、tools、tool_calls） |
| `agent/AgentTools.java` | 7 个工具的定义与执行 |
| `agent/AgentOrchestrator.java` | 编排：工具循环、多轮、强制兜底、收敛 |
| `agent/AgentProperties.java` | 配置绑定 |
| `service/impl/ChatServiceImpl.java` | 入口与降级判断 |
| `controller/ChatStreamController.java` | SSE 接口 |
| `frontend/src/api/chat.js` | fetch + ReadableStream 解析 SSE |

**Q3：关键配置项都是什么？为什么这么设？**
```yaml
canteen.agent:
  enabled: true            # 总开关，关掉就纯规则引擎（演示降级用）
  base-url: ...            # OpenAI 兼容地址
  api-key: ${CANTEEN_AGENT_KEY:...}   # 环境变量优先
  model: glm-5.3-flash
  timeout-ms: 30000        # 该模型带思考链偏慢，给足超时
  max-tool-rounds: 3       # 防模型死循环调工具
  history-limit: 8         # 多轮上下文，太多会烧 token
  temperature: 0.2         # 客服要稳定，不要发挥
  max-tokens: 800          # 限制单次成本
  fallback-to-rule: true   # 失败自动降级
```
- `temperature 0.2`：客服场景要的是"复述事实"，不是创作，温度高了会飘。
- `max-tool-rounds 3`：实测 1~2 轮就够，3 是安全上限，防止模型反复调工具拖死请求。

**Q4：为什么选这个模型？**
- 便宜 + 快 + 支持 Function Calling（工具调用是硬需求，不支持就做不了 Agent）。
- GLM-5.3-Flash 准确率更好（16/16），但延迟翻倍（平均 8.2s）；Qwen2.5-7B 是 2~4s。
- 诚实说法：「我们做了两轮模型对比测试，最终按准确率优先选了 GLM，用流式输出来缓解等待感；如果要求低延迟可以一行配置切回 Qwen。」

**Q5：换模型要改多少代码？**
- **零代码改动**，只改 `application.yml` 三行（base-url / model / timeout）。因为全部走 OpenAI 兼容协议，`LlmClient` 不认识任何厂商专有字段。

## 二、调用链类（必问）

**Q6：一次提问完整走哪些步骤？**
1. 前端 `ChatWidget` 调 `askChatStream(question, history)`；
2. `fetch('/api/chat/ask/stream')`，POST + `Accept: text/event-stream`，带 JWT；
3. 后端 `ChatStreamController.askStream` 返回 `SseEmitter`；
4. `ChatServiceImpl` 先试 `tryAgentStream`，失败返回 null 就走规则引擎；
5. `AgentOrchestrator` 组 messages（system prompt + 历史 + 本轮问题 + 工具定义）发给模型；
6. 模型返回 `tool_calls` → `AgentTools.execute()` 查库 → 结果作为 `role=tool` 消息回填；
7. 再请求模型，模型输出自然语言；
8. 后端把文本按增量通过 SSE 推给前端（`event: delta`），最后推 `event: done` 带完整 `ChatAnswerVO`；
9. 前端逐字渲染，收到 done 后用完整结构替换（含卡片）。

**Q7：为什么用 SSE 不用 WebSocket？**
- 需求是**单向**推送（服务端 → 浏览器），SSE 够用且更轻：走普通 HTTP、自动重连、不需要协议升级。
- WebSocket 是双向的，这里用不上，还得处理心跳和连接管理。

**Q8：为什么前端不用 EventSource，要手写 fetch 解析？**
- `EventSource` **只支持 GET，不能带自定义请求头**，我们既要 POST 传 question/history，又要带 `Authorization` 头。
- 所以用 `fetch` + `ReadableStream` 手工按 `\n\n` 切事件、按 `data:` 取内容（`frontend/src/api/chat.js`）。
- 这个点被问到的概率很高，答出来说明真自己写过。

**Q9：SSE 接口为什么单独建一个 Controller？**
- `text/event-stream` 没有对应的 `HttpMessageConverter`，全局异常处理器把它包成 JSON `Result` 时会二次抛出 `HttpMessageNotWritableException`，把真实错误盖掉。
- 所以在 `ChatStreamController` 里用**类级 `@ExceptionHandler`** 兜住，优先级高于全局处理器（源码注释里写明了这个坑）。

**Q10：多轮对话怎么实现的？历史存在哪？**
- 前端把最近若干轮 `{role, content}` 随请求一起传（`payload.history`），不落库。
- 后端 `historyLimit=8` 截断后再拼进 messages。
- 好处：无状态，服务重启不丢上下文；坏处：刷新页面历史就没了（当前产品设计如此）。

**Q11：流式怎么保证前端不会显示半截或乱码？**
- 按 `\n\n` 分帧、`TextDecoder(stream: true)` 处理跨包的多字节字符；
- 增量只用于"边打边显示"，`done` 事件到达后用完整答案覆盖一次，保证最终一致。

## 三、Agent 编排与工具（最能体现水平，重点准备）

**Q12：什么是工具调用（Function Calling）？你的 7 个工具是什么？**
| 工具名 | 作用 |
|---|---|
| `search_dishes` | 按关键词查菜品（名称/描述），返回价格、评分、窗口、图片 |
| `list_stalls` | 查档口列表（名称/窗口号/分类） |
| `list_stall_dishes` | 查某档口的菜，可只取招牌菜 |
| `get_rankings` | 榜单：热榜/避雷/新菜/档口 Top |
| `search_faq` | 制度问答知识库（评价、投诉、预约规则） |
| `list_notices` | 公告 |
| `get_overview` | 食堂整体概览（菜数、评价数、平均分） |

**Q13：为什么用工具查库，不直接把数据放进 prompt？**
- 数据量大：52 道菜 + 762 条评价，全塞进去 prompt 会爆 token、贵且慢；
- 数据会变：新菜、调价、新评价，塞进去就是过期快照；
- 工具是**按需精确查询**，模型只拿它需要的那几条，准确率和成本都更好。

**Q14：模型会不会乱调工具或者死循环？怎么控制？**
- `maxToolRounds = 3` 硬上限；
- 第 1 轮如果模型"只说话没查库"（`finish=stop, toolCalls=0`）而问题明显需要数据，会触发 `chatWithRequired()` 用 `tool_choice=required` **强制它调一次工具**；
- 最后一轮进入 `summarize` 阶段，追加指令「不要再调用工具，直接根据数据回答」，强制收敛。

**Q15：卡片里的价格评分是哪来的？模型说的还是数据库的？**
- **数据库的**。`AgentCardBuilder.build(result.toolResults())` 用的是工具返回的**原始结果**，不是模型输出的文本。
- 这是防幻觉的关键设计：模型只负责组织语言，数字一律以工具结果为准。

**Q16：多轮里说"它多少钱"、"这家怎么样"，怎么知道指谁？**
- 把最近 8 条历史一起给模型，由模型完成指代消解，再拆成工具参数（比如上一轮说了宫保鸡丁，"它"就解析成 `keyword=宫保鸡丁`）。
- 实测 4/4 通过（测试报告第二节）。

## 四、Prompt 设计（会问"你怎么写的提示词"）

**Q17：系统提示词怎么写的？为什么这么写？**
> 原文要点：你是食堂小助手 → 涉及菜品/价格/评分/档口/制度的问题**先调工具再回答** → **不要凭记忆编造价格、评分、菜名** → 制度类以 `search_faq` 的 answer 为准，不要另编流程 → 工具查不到就如实说没有 → 中文、口语化、120 字以内 → 点出菜名、窗口、价格。

- 核心是三条约束：**必须先查**、**不许编**、**查不到要说没有**。
- 加"120 字以内"是为了移动端气泡可读性，也顺带省 token。

**Q18：怎么防止模型瞎编（幻觉）？**
四层：
1. Prompt 明确禁止编造价格评分；
2. 强制调工具（`tool_choice=required` 兜底）；
3. 卡片数据取工具原始结果，不经模型；
4. 查不到时 prompt 要求如实说"没找到"（实测：问"佛跳墙多少钱"、"99 号窗口在哪"都正确回答没有）。

**Q19：制度类问题为什么不让模型自由发挥？**
- 制度（怎么投诉、怎么预约、评价能不能改）有**唯一正确流程**，模型改写会误导用户。
- 所以约定：制度类以 `search_faq` 返回的 `answer` 为准，按原文的做法和入口回答，不许另编。

**Q20：知识库改了什么时候生效？**
- 原版有 5 分钟缓存；这一版已修成**改完立即可问**（接入进度清单第 8 项）。
- 这是答辩可以主动讲的"迭代点"：从"有延迟"到"热更新"。

## 五、降级与异常（老师很爱问"模型挂了怎么办"）

**Q21：模型超时/欠费/断网，系统会崩吗？**
- 不会。`tryAgentStream()` 捕获 `LlmException` 后返回 null，`ChatServiceImpl` 继续走**原有本地规则引擎**（关键词加权 + 二元组覆盖率匹配）。
- 实测回退耗时 **77~576ms**，用户几乎无感。
- 配置 `fallback-to-rule: false` 时也可以改成直接提示"智能助手繁忙"，但我们默认开着降级。

**Q22：前端怎么知道现在用的是哪个引擎？**
- `GET /chat/engine` 返回当前引擎（`agent` / `rule`），客服窗口标题下会显示「智能问答」或「本地规则」，不欺骗用户。

**Q23：为什么保留规则引擎，不直接删掉？**
- 三个理由：① 断网/无 key 仍可用（课堂演示保险）；② 常见问题（几点营业、怎么投诉）规则引擎毫秒级，比调模型快 10 倍；③ 成本为零。
- 定位是**互补**，不是过渡方案。

**Q24：有没有重试机制？**
- 没有做自动重试。理由：模型 30s 超时已经很长，重试只会让用户等更久、成本翻倍；失败即降级更快。

## 六、性能与成本

**Q25：响应多快？为什么慢？**
- GLM-5.3-Flash：平均 **8.2s**，最慢 14.9s（含思考链）；Qwen2.5-7B：2~4s。
- 缓解手段：**流式输出**——首字 1~2s 就出来，用户能看到"正在打字"，体感远好于转圈等 8 秒。
- 优化方向：换小模型/开缓存/把高频问题（价格类）走规则引擎前置拦截。

**Q26：一次问答花多少 token？成本怎么控？**
- `max-tokens 800` 限制输出；工具返回只给必要字段（`limit` 默认 5、最大 8）；历史截断 8 条。
- 高频简单问题走规则引擎，不花 token。

**Q27：并发高了会怎样？**
- 线程池会被慢请求占满（单次 8s）。当前是课程项目、几十人规模可接受。
- 改进：模型调用异步化 + 信号量限流 + 缓存相同问题的答案。

## 七、安全（必问，且有一个必须提前处理的风险）

**Q28：API Key 怎么保管的？**
- 配置写法是 `${CANTEEN_AGENT_KEY:默认值}`，**优先读环境变量**。
- 正确回答：「Key 通过环境变量注入，代码库不提交真实 key。」

> ⚠️ **提交/演示前必须处理**：`application.yml` 第 48 行的 `api-key` 还带着**明文默认值**（`4bd1576d...`）。这份代码一旦交上去或被拷走，key 就泄露了，别人可以刷你的额度。
> 建议改成 `api-key: ${CANTEEN_AGENT_KEY:}`（不给默认值），本地用环境变量或 `.env` 传；如果这个 key 已经在群里/仓库里出现过，去智谱后台**重新生成一个**。

**Q29：用户能不能通过提问诱导模型干坏事（提示注入）？**
- 模型没有任何写权限，7 个工具**全是只读查询**，最坏结果是答非所问，改不了数据。
- 系统提示词限定角色与话题范围，越界问题会拒答或兜底。

**Q30：用户提问内容直接进 prompt，有注入风险吗？**
- 有理论风险（比如"忽略上面的指令"），但危害被工具只读 + 结果由 `AgentCardBuilder` 二次组装限制住了；
- 用户输入在前端是插值渲染（自动转义），不会 XSS。

## 八、可能被问倒的「硬问题」预案

**Q31：为什么不用 RAG（向量检索）？**
- 我们的数据是**结构化**的（菜名、价格、评分、档口），用 SQL 精确查比向量相似度更准，还能算聚合（平均分、榜单）。
- 向量检索适合非结构化长文本（制度文档）；我们的制度只有 24 条，关键词 + 工具查表就够。
- 如果以后制度文档变多（几十页 PDF），可以上 RAG。

**Q32：Agent 和普通调用 API 有什么区别？**
- 普通调用：一次问答，模型只能靠上下文。
- Agent：模型能**决定调哪个工具、传什么参数、调几次**，后端执行后再让它总结——本质是"模型 + 工具"的循环。

**Q33：模型返回的 tool_calls 参数是 JSON，解析失败怎么办？**
- `parseArgs()` 做了容错（空串、非法 JSON 都退化成空 Map），工具内部再对参数做默认值和上下限处理（`limit` 最大 8）。

**Q34：这套东西是你自己写的还是抄的？**
- 能讲出踩过的坑就够说服力，挑两个说：
  1. 第 1 轮模型常常"只说话不查库"（`finish=stop, toolCalls=0`），所以加了 `tool_choice=required` 强制兜底；
  2. SSE 异常被全局处理器二次包装，才单独拆出 `ChatStreamController` 用类级异常处理。

## 九、现场演示脚本（3 分钟）

1. **常规查询**（体现实时查库）：问「宫保鸡丁多少钱」→ 卡片显示价格 + 窗口，指出「这个 12 元是数据库里的，不是模型背的」。
2. **多轮指代**：接着问「它辣吗 / 它在哪个窗口」→ 证明理解上下文。
3. **新数据识别**（杀手锏）：管理员现场新增一道菜 → 立刻问它的价格 → 正确答出，说明「工具实时查库，不是训练数据」。
4. **不存在的数据**：问「佛跳墙多少钱」→ 如实说没找到，证明不编造。
5. **降级演示**（加分）：把 `enabled` 改 false 或断网 → 再问一次，仍能回答（走规则引擎），窗口标题变成「本地规则」。
6. **流式效果**：指出答案是一字一字冒出来的，不是等 8 秒一次性出现。

**演示注意事项**
- GLM 慢（8s+），提问后**先说一句「它正在查库」**，别冷场；
- 提前把后端跑热（第一次请求最慢）；
- 准备一个录屏兜底，万一现场网络/额度出问题直接放录屏。

## 十、和原版的差异（老师若问"你们组改了什么"）

| 项 | 原版 | 现在 |
|---|---|---|
| 客服实现 | 纯规则匹配（关键词 + 二元组），命中率 95.5% | 大模型 Agent + 7 个工具 + 规则引擎降级 |
| 数据来源 | SQL 直接拼答案 | 模型决定查什么，工具实时查库 |
| 交互 | 一次性返回 | SSE 流式逐字输出 |
| 多轮 | 无上下文 | 8 条历史 + 指代消解 |
| 换模型 | — | 改 yml 三行，零代码 |
| 附带修复 | — | 首次评价失败、删除后无法再评、白名单丢失登录态三个 Bug |
